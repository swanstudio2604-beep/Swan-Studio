8. If a requested feature exceeds a free-tier service's capability, explain the limitation and suggest the simplest practical alternative.

## 8. Cart and checkout

### Cart

Add items, change quantity, remove items, item subtotals, cart total, apply/remove coupon, continue shopping, proceed to checkout. Persist in `localStorage` (`swan_cart`) for convenience, storing **only product IDs, variant and quantity**. Treat all stored data as untrusted. Display prices come from a fresh database read; the backend revalidates everything at order time.

### Checkout

Collect: name, email, phone, address, city, state, postal code, optional notes. Display items, quantities, subtotals, coupon discount, shipping (if configured), final amount in ₹.

**Order creation is a single trusted operation** (database function `place_order` or an Edge Function) that, in one transaction:

1. Authenticates the caller (or supports guest checkout only if explicitly decided; default is logged-in customers).
2. Loads real product prices, sale prices, stock and made-to-order status from the database.
3. Rejects unavailable, archived or out-of-stock items.
4. Validates and applies the coupon (Section 10).
5. Applies shipping rules from settings.
6. Calculates the final total in the database.
7. Decrements stock safely (row locks or conditional updates) to prevent overselling.
8. Inserts the order, immutable `order_items` snapshots (name, price, quantity at time of order) and the payment record with status `PENDING_VERIFICATION`.
9. Records coupon usage.
10. Returns the order ID and amount payable.

Prevent duplicate submissions (disable the button on submit and use an idempotency key stored with the order). Do not tell the customer an order exists until the backend confirms it. The client never sends a total or discount amount that the server trusts.

## 11. Manual UPI payment

No payment gateway in this version.

**Customer flow:**
1. Customer places the order.
2. Checkout/confirmation shows UPI ID `9509966512@fam` (from settings, not hard-coded in many places), a **Copy UPI ID** button and clear instructions.
3. Optional standard UPI deep link (`upi://pay?pa=...&pn=Swan%20Studio&am=...&cu=INR&tn=Order%20<id>`). Never assume opening the app means payment succeeded.
4. Customer submits a transaction/reference ID. An optional screenshot is allowed only if secure private storage is configured (type and size limits).
5. Payment record status is `PENDING_VERIFICATION`.
6. Message shown: **"Your order has been placed. Your payment is awaiting verification."**

The customer can only add a reference ID or screenshot to their own pending payment. They can never change its status.

**Admin verification:** view pending payments, order total and customer details, submitted reference ID, open the order, mark **Paid** or **Rejected**, add internal notes, and see who changed the status and when. The admin must check the real bank/UPI account first. Every decision writes a row to `payment_audit_log` via a trusted function (not a direct table update).

### Statuses (kept separate)

- **Payment:** `PENDING_VERIFICATION`, `PAID`, `REJECTED`, `REFUNDED` (only when a refund was actually processed).
- **Order:** `PENDING`, `CONFIRMED`, `PROCESSING`, `SHIPPED`, `DELIVERED`, `CANCELLED`.

An order is not confirmed merely because a transaction ID was entered. Cancelling an order restores stock via a trusted function. Show revenue totals only from orders with `PAID` payments; never count pending or rejected payments as revenue.

## 15. Database design

Beginner-readable `supabase/schema.sql` with a plain-language comment on every table. Use database-generated UUIDs, timestamps (`created_at`, `updated_at`), foreign keys, check constraints, indexes. Use `numeric(10,2)` (or integer paise) for money, **never floating point**.

| Table | Purpose |
|---|---|
| `profiles` | One row per auth user: name, phone, role (`customer`/`admin`) |
| `categories` | Collection names, slugs, images, sort order |
| `products` | Catalogue: price, sale price, stock, made-to-order, status, featured |
| `product_images` | Ordered image URLs and alt text per product |
| `product_variants` | Colors or sizes, only if needed |
| `addresses` | Saved delivery addresses, only if needed (avoid duplicating data) |
| `orders` | Order header, status, totals, shipping details snapshot, idempotency key |
| `order_items` | Immutable snapshot of name, price, quantity at order time |
| `payments` | Payment status, submitted reference ID, optional screenshot path |
| `payment_audit_log` | Who changed payment status, when, old/new value, notes |
| `coupons` | Coupon rules and limits |
| `coupon_usage` | One row per redeemed coupon per order and user |
| `wishlist` | Saved products per customer (optional) |
| `custom_orders` | Custom request details and status |
| `site_content` | Editable key/value content (announcement, hero, story) |
| `gallery_items` | Gallery images and captions |
| `site_settings` | UPI ID, WhatsApp number, shipping rules, low-stock threshold |

Do not add tables not needed for the initial implementation. Order records must stay correct after products are later edited or archived.

### Row Level Security (summary)

- **RLS enabled on every table.** Default deny.
- Public (anon) can **read** only published products, categories, product images, visible gallery items and non-sensitive site content/settings. Never expose UPI-sensitive or customer data beyond what is intentionally public.
- Customers can read/update only their own profile (excluding `role`), read only their own orders, order items, payments and custom orders, and manage their own wishlist.
- Customers cannot insert directly into `orders`, `order_items`, `coupon_usage` or update `payments.status`. They use trusted functions only.
- Admin access uses `is_admin()` checks. Admin-only: product/category/coupon/content management, order status changes, payment verification, reading all orders and custom orders.
- Storage buckets: public bucket for product images (admin write only); **private** bucket for payment screenshots and custom-order references with size and type limits and owner/admin access only.

### Trusted functions (SQL RPC or Edge Functions)

`validate_coupon`, `place_order`, `submit_payment_reference`, `admin_verify_payment`, `admin_update_order_status` (including stock restore on cancel), `admin_adjust_stock`. Each checks the caller, validates input, runs in a transaction and returns safe error messages.
